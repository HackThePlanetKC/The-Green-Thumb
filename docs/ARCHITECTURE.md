# Green Thumb — Architecture & Design Decisions

Full technical spec: MQTT topics, thresholds, calibration/pairing state machines, BLE GATT schema, and every design decision made along the way. See [`README.md`](../README.md) for the project overview.

Self-contained indoor plant growth helper. ESP32-C3 Super Mini base board, MicroPython firmware, MQTT to a Home Assistant Mosquitto broker via custom HACS integration. Expandable via BLE-connected peripheral modules.

## Hardware (base board)

- ESP32-C3 Super Mini
- DHT11 (temp/humidity)
- Analog capacitive soil moisture sensor v1.2
- Photoresistor (LDR) light sensor - planned swap to BH1750 I2C lux sensor
- SSD1306 128x64 OLED display (I2C)
- WS2812 addressable RGB LED (status/health color, pairing indicator)
- Physical pushbutton (short press: cycle display / long press 3s: BLE pairing mode)

Units: imperial (°F, foot-candles).

## Architecture

- Firmware: MicroPython, asyncio-based task loop
- Base board is the sole WiFi/MQTT/HA gateway - modules never connect to WiFi or HA directly
- Base acts as BLE central; future modules (pump, grow light, NPK sensor) are BLE peripherals
- HA integration: custom HACS component (not ESPHome, not generic MQTT discovery)
- Fallback: lightweight web portal served from the ESP32 for non-HA users, using the same internal command state machines as the HACS integration (no duplicate logic paths)

## `modules/` — peripheral/module development

`modules/` is the home for all module-specific code going forward (camera module now; pump, grow light, NPK sensor, and any future modules later) - kept entirely separate from the base station's own `core/`/`drivers/`/`web/` layout above. That separation matters because modules on this platform are not guaranteed to be MicroPython/ESP32 at all: a module can be BLE-paired firmware running on the same class of microcontroller as the base (matching the `module/<mod_id>/*` MQTT relay contract documented below), or it can be an entirely standalone device on different hardware/OS with its own MQTT identity - the Camera Module (see next section) is the first example of the latter, running on a Pi rather than an ESP32. Each subdirectory under `modules/` is a self-contained codebase: its own config, its own version (if it has one), its own build doc - nothing under `modules/` is compiled, flashed, or deployed as part of the base station's own build (`tools/build_mpy.sh` does not touch it).

**Camera Module** (`modules/Camera Module/`) - a standalone Pi-based visual health monitor: periodic photos of the plant, with a WS2812B RGBW ring (7 pixels) for low-light fill flash, driven directly off GPIO18 (Pi hardware PWM0) via `rpi_ws281x`. Not a BLE-paired peripheral of a base station (unlike the provisional module development contract further down this doc, which describes modules connecting *through* a base) - this module speaks MQTT directly and independently, subscribing to whichever base(s) it's monitoring rather than relaying through one. That independent MQTT presence is the reason `device_info`'s `friendly_name` field exists (see below): this module needs a human-readable label for the base(s) it's attached to, and reading a base's retained `device_info.friendly_name` gives it one without duplicating the base's `device_name` lookup logic itself. Full detail: [`modules/Camera Module/README.md`](../modules/Camera%20Module/README.md) and [`BUILD.md`](../modules/Camera%20Module/BUILD.md).

Built so far: the flash subsystem (ring driver, trigger logic, config); WiFi setup + MQTT base-discovery/association; grid/region layout and per-base settings scoping; the wilt-watch and drama-level comparison metrics; and this module's own top-level MQTT/HA presence for global settings. Not yet written: capture scheduling itself (when a photo actually gets taken) and the light sensor driver `flash_controller.maybe_flash()` reads from.

**Grid layout (`grid_config.py`)** divides the camera's frame into up to 4x4 regions - rows and columns are independent bounds, so non-square layouts (2x4, 1x3, etc.) are fully supported, not just square presets - and maps each cell to one of this module's associated bases. A base may be assigned more than one cell; those cells are expected to be contiguous, but contiguity itself is **not validated** - the web portal's click-to-assign UI makes an accidental non-contiguous assignment unlikely, and adding real flood-fill/graph-connectivity validation for a constraint that's already hard to violate by accident wasn't judged worth the complexity. `cell_pixel_bbox()` maps a base's assigned cell(s) to a pixel bounding box against a given reference photo's dimensions, dividing the frame evenly across the grid - used by the wilt-watch reference-capture flow to know which crop belongs to which base. Grid config is module-global: stored in this module's own config, editable only via the camera portal or HA, never from an individual base's own portal.

**Settings scoping (`per_base_settings.py` + config.py)** splits settings into two tiers:
- **Module-global** (camera portal + HA only): capture frequency, grid layout/assignment, and flash on/off + low-light threshold.
- **Per-base** (camera portal + HA, keyed by `base_id` - see `per_base_settings.py`): general health (always on, not a toggle - there's no config value for something that can never be anything but `True`) plus five independent opt-ins: chlorosis, necrosis, spotting, wilt-watch, drama-level. Enabling one never implies another. **A given base's own portal editing only its own settings is explicitly NOT built here** - see the gap recorded in `decisions-and-practices.md` and Future Enhancements below for why, and what closing it would actually require.

**Wilt-watch and drama-level (`wilt_watch.py`, `drama_level.py`, `image_compare.py`)** are both structural (shape/position), not color-based, comparisons between a region crop and a second image - deliberately kept separate from the not-yet-built, species-agnostic health classifier (see the species-threshold Future Enhancement below), which is a color/appearance question, not a droop/turgor one. They share one comparison primitive (`image_compare.structural_difference()` - a per-column "first dark pixel from the top" silhouette-edge profile, compared column-by-column; a documented starting algorithm, not validated against real plants yet, same "tune once pointed at a real plant" spirit as this module's light/flash thresholds) and differ only in which second image they keep on disk:
- **Wilt-watch** compares against a stored **reference** image, captured once per base's region. Turning wilt-watch on for a base that has no reference image yet sets a `wilt_watch_config_necessary` flag (surfaced in the portal and in that base's own MQTT/HA state) - no wilt level is computed until a reference exists. The reference is stored locally on the module's filesystem, never published over MQTT (unless the separately-planned image-passthrough option is also enabled, which doesn't exist yet).
- **Drama-level** compares against the **immediately previous** capture of the same region, no reference or config-necessary step needed - it represents rate of change between consecutive captures, not absolute severity, and updates its stored "previous" image every call.

Both are computed independently per base, since `capture_still()` (`camera_capture.py`) - a minimal, injectable "take one photo right now" wrapper around `rpicam-still` - is the only piece of real camera I/O either needs; actual periodic capture scheduling is still not built (see README.md "Remaining"), so today both metrics are only exercised through the portal's manual reference-capture flow, not a live capture loop.

**This module's own MQTT/HA presence (`mqtt_presence.py`)** publishes two deliberately isolated topic trees over its own, separate paho-mqtt connection (distinct from `mqtt_discovery.py`'s own connection - two connections from one process is a real but minor resource cost, judged simpler than mixing "learn what bases exist" and "publish/handle this module's own settings" into one class and its one test file; revisit only if connection overhead is ever a measured problem):
- `greenthumb/camera/<camera_id>/global/...` - module-global settings ONLY (see the topic tree below). One minimal HA device card for the camera module itself. Per-base health/metric data must never appear here.
- `greenthumb/<base_id>/module/<camera_id>/...` - per-base settings, reusing the base station's own documented `module/<mod_id>/*` topic shape (below) so each base's settings attach to that base's own existing HA device. Normally that shape is populated by a base relaying a BLE-paired module's data; here the Camera Module (which has its own direct MQTT connection, not a BLE pairing) publishes into it directly, with `camera_id` standing in for `mod_id`.

A generic `set_config` command (global topic, `{"action": "set_config", "path": ..., "value": ...}`, mirroring `core/mqtt_client.py`'s own handler shape) is restricted to a fixed whitelist of top-level config keys (`capture`, `grid`, `flash`) - it can never touch this module's own WiFi/broker credentials or association list, even though they live in the same `config.json`. Per-base settings use a narrower `set_metric` command instead (`{"action": "set_metric", "metric": ..., "enabled": ...}`), since a base can only ever toggle its own five-item metric set.

**WiFi setup (`wifi_manager.py`) and MQTT discovery/association (`mqtt_discovery.py`, `base_association.py`)** mirror the base station's own onboarding shape - a setup AP at first boot, a portal for entering connection details, "try it now and report success/failure, but save regardless" - while adapting the implementation to the actual platform rather than forcing MicroPython patterns onto Pi/Linux code:

- **WiFi**: `nmcli` (NetworkManager, Raspberry Pi OS's default network stack) instead of a MicroPython `network.WLAN()` object. Fully synchronous, unlike the base's async `WifiManager` - nothing else in this module runs an asyncio event loop, so forcing one `async def` here for API-shape parity alone would only add sync/async bridging with no functional benefit. AP-mode gateway is `10.42.0.1` (NetworkManager's own hotspot default), not the base's `192.168.4.1` - a fact about the platform, not a project-wide convention.
- **MQTT broker address is bundled into the WiFi setup step**, unlike the base station (which defers broker configuration to a settings page reached over a network connection it already has by then). This module's very next setup step - base discovery - needs a broker connection to function at all, and no broker auto-discovery mechanism exists anywhere in this project (the base's own settings page requires manual entry too), so there was no existing precedent to reuse instead.
- **Discovery** subscribes to `greenthumb/+/device_info` (paho-mqtt, `CallbackAPIVersion.VERSION2` pinned explicitly) and builds a live `{base_id: {friendly_name, device_name, version}}` map as retained messages arrive - no pre-configured base list needed. A base only needs to have been online once, ever, for this module to learn about it (device_info is retained).
- **Association is stored by `base_id`, never `friendly_name`** - the latter is a display-only, user-editable label that can change at any time (see `friendly_name`'s own entry below), and using it as a stored key would silently break the association on a rename.
- **The web portal** (`web_portal.py`) uses Python's standard-library `http.server` rather than a hand-rolled async server like the base's `web/server.py` - that approach exists there because MicroPython's whole `main.py` runs one asyncio event loop and a vendored framework's overhead isn't worth it on an ESP32-C3's limited RAM. Neither constraint applies on a Pi, so reimplementing HTTP parsing a second time for a different platform would be duplicated effort with no benefit - the standard library already provides it.

## Key design decisions

**Timing:**
- Local sensor sampling: every 2 min
- MQTT state publish: every 30 min default, runtime-adjustable via command
- Interrupt publish: immediate, only on transition to red health status
- Display auto-cycle: every 10s, resumes 20s after a manual button press
- Display night mode: configurable time range (default 22:00-07:00), display off outside manual wake; a button press during night mode wakes to that screen for 20s (same idle timer as normal), then re-sleeps

**MQTT topic tree:**
```
greenthumb/<base_id>/status                      (LWT, retained)
greenthumb/<base_id>/state                        (JSON, retained)
greenthumb/<base_id>/health                       (JSON, retained)
greenthumb/<base_id>/config                       (JSON, retained - full current user-configurable settings, republished after every change)
greenthumb/<base_id>/device_info                  (JSON, retained - version/device_name/friendly_name/base_id, fixed-per-boot facts, not user-editable config)
greenthumb/<base_id>/command                      (JSON, not retained)
greenthumb/<base_id>/light_summary                (JSON, retained, published daily at midnight)
greenthumb/<base_id>/light_hours_today             (JSON, retained, published on-demand via {"action": "get_light_hours_today"})
greenthumb/<base_id>/calibration/command
greenthumb/<base_id>/calibration/status           (retained)
greenthumb/<base_id>/pairing/command
greenthumb/<base_id>/pairing/status               (retained)
greenthumb/<base_id>/module/<mod_id>/status
greenthumb/<base_id>/module/<mod_id>/state
greenthumb/<base_id>/module/<mod_id>/command

greenthumb/camera/<camera_id>/global/status       (LWT, retained)
greenthumb/camera/<camera_id>/global/device_info  (JSON, retained - version/camera_id)
greenthumb/camera/<camera_id>/global/config       (JSON, retained - module-global settings only: capture, grid, flash)
greenthumb/camera/<camera_id>/global/command      (JSON, not retained - generic set_config, whitelisted to capture/grid/flash)
```
QoS 1 everywhere. `<base_id>`/`<mod_id>` derived from MAC address. `<camera_id>` derived the same way but from the Camera Module's own WiFi interface MAC (see `modules/Camera Module/identity.py`) - visually consistent with `<base_id>`/`<mod_id>` but never compared to or sharing a namespace with either. The Camera Module also publishes its per-base settings into `greenthumb/<base_id>/module/<camera_id>/{status,state,command}` - reusing the `module/<mod_id>/*` shape above, but published directly by the Camera Module's own MQTT connection rather than relayed by the base (see the Camera Module section above for why that's a legitimate reuse of the same shape rather than a new one).

**A real gap caught while starting the HACS integration scaffold, fixed immediately:** `state`'s periodic publish (`publish_loop()` in `main.py`) was missing `light_level_label` - the web dashboard's `/api/state` already included it, but the MQTT topic HA would actually consume didn't. A Light Level sensor in HA would have had no data source. Fixed by adding it to the same dict literal.

**Multiple base stations - what's already handled, and what isn't yet:**

Every topic above is prefixed with `<base_id>`, so two base stations on the same home network/broker never collide at the MQTT level - `greenthumb/AABBCC/module/.../...` and `greenthumb/DDEEFF/module/.../...` stay fully separate even for modules of the identical type paired to different bases. Each base's module registry (`module_manager.py`'s `_REGISTRY_PATH`) also lives on that base's own flash - no cross-base coordination or shared state exists, so nothing on one base can corrupt or overwrite another's data. `mod_id` (derived from a module's own BLE serial) is scoped by the `base_id` prefix in every topic it appears in - even in the unlikely event two different physical modules paired to different bases hash to the same `mod_id`, their topics remain distinct because `base_id` differs. The AP-mode setup SSID (`GreenThumb-Setup-<base_id>`) is unique per device for the same reason.

**Theoretical collision risk, worth naming honestly (not a practical concern for a home setup):** `base_id` is only 3 bytes (16.7M possible values) - collision probability for a handful of devices is astronomically low, but it isn't a cryptographic guarantee. If absolute uniqueness ever mattered (e.g. dozens of units), the fix would be switching to the full 6-byte MAC, at the cost of longer topic strings - not done here since the tradeoff isn't worth it at any realistic hobbyist scale.

**The one collision risk that DOES need active design care, for whenever the HACS integration gets built:** Home Assistant's entity/device registry is the one place state is genuinely shared/centralized across multiple bases (unlike each base's isolated MQTT namespace). If that integration ever keys entities or devices by `mod_id`/`type` alone, without folding in `base_id`, two modules of the same type on different bases (a "Pump" on Base 1 and a "Pump" on Base 2) would collide in HA's registry. **Every entity and device `unique_id` in the future integration must incorporate `base_id`**, not just `mod_id` or `type` alone - the single most important constraint to remember when that work starts.

**The "Base 1: Pump, Light / Base 2: Pump, NPK" grouping maps directly onto Home Assistant's built-in device hierarchy - `via_device`.** Each base registers as its own HA device; each paired module also registers as its own HA device, with `via_device` pointing back to its base's device identifier. HA's own UI already groups/nests child devices under their parent automatically - no custom dashboard card or special code needed for the grouping itself, just correct device registration in the integration. Documented here as the intended design for when the HACS integration is built (not yet started), so it isn't accidentally designed differently later.

**One genuine physical-layer edge case, not really fixable in software:** if two base stations are both in active BLE pairing/scanning mode at the same time and within radio range of each other, both could see the same advertising module in their candidate list. If a user accidentally selects and pairs the same physical module to both bases, only one can hold an active BLE connection to it at a time (most BLE peripherals support one central connection) - the other base's registry entry would just show that module as persistently offline, not corrupt any data. Not something the base can prevent alone (there's no cross-base coordination channel, deliberately, to keep bases independent) - the practical mitigation is just not running two pairing sessions in the same room at the same time.

**HA-visible/writable configuration:** every user-configurable setting (thresholds, calibration values, timing, display/night-mode) is readable via the retained `config` topic and writable via a single generic command:
```json
{"action": "set_config", "path": "thresholds.temp_f.green_min", "value": 66}
```
`path` uses dot notation into the config schema (see `core/config.py`'s `get_by_path`/`set_by_path`). An invalid or typo'd path is rejected (`KeyError`) rather than silently ignored or creating a new key. This replaces per-setting bespoke commands (earlier drafts had `set_interval`, `set_night_mode` individually) with one mechanism that covers the whole schema.

**Explicitly excluded from HA-visible config:** WiFi credentials and MQTT broker address/credentials. The device can't receive MQTT commands before it already has WiFi and a broker connection, so exposing those over MQTT is circular, and broker credentials shouldn't travel over MQTT regardless. These stay in the initial-setup web portal flow only.

**Open item resolved:** an invalid `set_config` path or value is rejected silently by `mqtt_client.py` - no ack/error topic exists anywhere in this design, so the retained `config` topic simply not changing is the implicit signal back to HA that the write didn't take.

**MQTT client library: umqtt.simple, not umqtt.robust (deviation from earlier plan).** `umqtt.robust` was the originally vendored choice for its automatic reconnect. On closer inspection, its reconnect works by catching `OSError` and **blocking in an internal retry loop** until the broker comes back - which would stall the entire asyncio event loop (display, sensors, BLE) during a broker outage. That's inconsistent with `wifi.py` and `ntp.py`, both of which deliberately built their own async, non-blocking connect/backoff logic rather than trusting a library's blocking retry. `mqtt_client.py` does the same: plain `umqtt.simple`, with its own `reconnect_forever()` task handling backoff asynchronously (1s, 2s, 4s... capped at 60s, same pattern as the other two). `check_msg()` (umqtt.simple's non-blocking poll variant, not the blocking `wait_msg()`) is polled every 200ms from `listen_forever()`. Individual `connect()`/`publish()` calls remain blocking under the hood, but are short (small JSON payloads on a local network) - the same accepted tradeoff already made in `wifi.py`'s `connect_sta()` and `ntp.py`'s `sync_once()`.

**mqtt_client.py responsibilities:** topic construction (`greenthumb/<base_id>/...`), LWT setup (`status` topic, "offline", retained, set before `connect()`), publish helpers matching every topic in the tree above (`publish_state`, `publish_health`, `publish_config`, `publish_light_summary`, `publish_calibration_status`, `publish_pairing_status`, `publish_module_state`, `publish_module_status` - all QoS 1, retained where specified), and command dispatch: `set_config` is handled directly against the live config dict (shared by reference with the rest of the firmware, so a change is visible everywhere immediately); all other command actions are handed off via callbacks (`on_command`, `on_calibration_command`, `on_pairing_command`, `on_module_command`) to whichever module actually owns that logic (`health.py`, `calibration.py`, `pairing.py`, `module_manager.py` - none written yet).

**Health thresholds** (user-configurable per plant profile, generic houseplant defaults shown):

| Metric | Green | Red | Source |
|---|---|---|---|
| Temperature | 65-75°F | <50°F or >90°F | Sourced (chilling injury / heat stress references) |
| Humidity | 40-60% | <20% or >80% | Sourced |
| Light | 200-500 fc | **unset - see open items** | Green range sourced; red thresholds not yet sourced |
| Soil moisture | 20-40% | <10% or >50% | User-specified |

**Soil moisture calibration:** MQTT-driven state machine (`start` -> `read_dry` -> `read_wet` -> `save`/`cancel`), 10 samples averaged over ~2s per read. Shared between web portal and HACS integration - one state machine, two entry points. Moisture % computed via linear interpolation between the two calibrated raw readings (dry_raw -> 0%, wet_raw -> 100%) - sensor polarity not assumed, only the two labeled endpoints. Raw values are on the `machine.ADC.read_u16()` scale (0-65535, portable across MicroPython ports), not a raw 12-bit ADC count.

**Light calibration (`core/calibration.py`):** same state machine shape (`start` -> `read_dark` -> `read_bright` -> `save`/`cancel`), but `save` additionally requires a user-supplied `bright_fc` reference value - unlike soil (always 0-100%), the device has no way to know the actual fc level it's being held up against during calibration. `light_calibration.min_delta_raw` (placeholder, same 5%-of-uint16-range reasoning as `soil_calibration.min_delta_raw`) validates the two readings differ enough to be meaningful.

**Calibration failure handling is asymmetric by design:** an insufficient delta between the two raw readings (either target) forces a full restart back to idle - the actual sensor readings were the problem, so redoing the physical measurement is the only fix. A `save` missing `bright_fc` (light only) stays in `awaiting_save` instead - the readings were fine, only the save command itself was incomplete, so retrying `save` with the value added is the correct recovery without re-measuring anything. There's no MQTT ack channel anywhere in this design (see the `set_config` note above); `calibration/status` being retained (not one-shot) is what lets both the web portal and HA see the current state/error at any time, including after a rejection.

**Light duration tracking (`core/light_tracker.py`):** separate from instantaneous fc reading.
- `light_present_threshold_fc`: 75 (sourced - "just enough daylight to read by")
- `light_hours_target`: 12-16h/day (sourced)
- `high_intensity_hours` (optional direct-light target): tracked the same way as `light_hours_target`, evaluated as a separate, non-overriding status - see the Settings page section below for the full writeup, including the gap it started as and the gating logic.
- Evaluated once daily at midnight rollover, not live - status reflects "yesterday". `check_rollover(current_local_date, ...)` compares against the last-seen date (from `ntp.local_date()`); a change triggers a summary and resets both counters. The very first call ever just records the starting date and returns `None` - there's no "completed day" yet to summarize.
- Summary status is **green or yellow only, never red** - `light_hours_target` only ever had a green range specified (no red tier), so inventing one here would repeat the same mistake as guessing `light_fc.red_max`. Reasons: `"below_target_hours"` / `"above_target_hours"`.

**Display screens:** confirmed core order, each with a 16x16 monochrome bitmap icon (`drivers/icons.py`), rendered via `Display.draw_screen(icon_bytes, title, lines)`:

| # | Screen | Icon |
|---|---|---|
| 1 | Temp + Humidity | Thermometer |
| 2 | Soil Moisture % | Droplet |
| 3 | Light (fc) | Sun |
| 4 | Overall health status | Heart |
| 5 | WiFi/MQTT connection + IP | WiFi arcs |

**Extensible module screens:** `Display.add_screen(screen_id, render_fn)` / `remove_screen(screen_id)` let future BLE modules insert their own screen when they pair and remove it when they unpair, without `display.py` or `main.py` knowing about module types in advance. `draw_screen()` is the standard format any module's render_fn should target - an icon (use `icons.ICON_MODULE` as a generic fallback if the module has no custom icon), a title, and up to 5 lines of body text. `display.py` has no built-in knowledge of any module's payload shape; `module_manager.py` supplies the actual per-module-type render function when a module pairs. Whether module screens carry their own custom icon or always use the generic gear fallback is not yet decided - deferred until the first real module (watering pump) is built.

**Display night mode:** optional (`display.night_mode.enabled`, default on but fully user-toggleable), runtime-adjustable from Home Assistant via the generic `set_config` command, e.g.:
```json
{"action": "set_config", "path": "display.night_mode.enabled", "value": false}
```
**Status LED (`status_led.py`):** single WS2812, diffused under a thin printed section of the enclosure (a 3D-printed near-life-size fist/thumbs-up; LED sits under the thumbnail, display sits on the middle finger's face).

**Boot animation:** plays automatically from power-on until `set_health()` is first called with real data. Rather than inventing a 4th "unknown" health color, there's a dedicated startup sequence: a 3-second warm-to-cool white "sunrise" (linear brightness ramp 0-30% of configured brightness, RGB blended between ~2000K `(255,147,41)` and ~7000K `(243,242,255)` reference approximations - not a precise CCT formula, since WS2812 has no dedicated white channel anyway), followed by breathing green - a general "still initializing, not ready yet" standby indicator, not just a boot-specific tail end, continuing for as long as needed. Priority: the sunrise (0-3s) is fully protected from interruption. Breathing green gets a further 5s grace window (3-8s total) where it's also protected. Only after that (8s total) can pairing or WiFi-connecting preempt the still-ongoing breathing green - and if those clear before `set_health()` is ever called, breathing green resumes underneath them, since the device is still "booting" the whole time. Night-mode suppression never applies to any part of this, at any point.

Solid green/yellow/red for health status. If red persists continuously past a configurable delay (`status_led.red_escalation_delay_s`, default 3600s - a UX choice, not a sourced threshold), the LED switches from solid to **blinking** red and fires a `requires_immediate_attention` flag, added to the `health` MQTT payload:
```json
{
  "status": "red",
  "reasons": ["soil_moisture_low"],
  "requires_immediate_attention": true
}
```
This flag flip (either direction) also triggers an immediate out-of-cycle publish, same as the original red-transition rule. Pairing mode (blinking blue) overrides the health display entirely while active, and always bypasses night-mode suppression - it's a deliberate action the user just triggered. WiFi connecting/reconnecting shows as **breathing purple** (smooth sine-based brightness ramp, not a hard blink) - unlike pairing, this respects night-mode suppression, since a reconnect can happen unattended at any hour and there's no reason to light up a dark room over something the user didn't initiate. Night mode's `led_off` suppresses the LED, but **only the escalated/blinking red tier** can override that suppression, and only if `display.night_mode.red_overrides_led_off` is enabled (default off) - plain solid red never overrides night mode, and neither does the breathing-purple WiFi state. `status_led.brightness` (default 0.15, a 0.0-1.0 scalar) is a placeholder pending real tuning once the physical diffused enclosure exists.

Priority order in `tick()`: boot animation > pairing > WiFi connecting > health display.

**Health calculation (`health.py`):** pure function, `evaluate_health(readings, thresholds_cfg)` -> `{"status": ..., "reasons": [...]}`. Overall status is the worst of all evaluated metrics (red > yellow > green). A metric with a `None` reading (sensor unavailable or uncalibrated) is excluded from aggregation entirely - never counted as green, since a missing reading isn't a good reading. If literally every metric is `None`, overall status is `None` too, a distinct case from boot (which never calls into this module at all - see status_led.py's boot animation above) or from a single metric being unavailable. This module makes no publish or LED decisions itself; it only computes.

`display.night_mode.led_off` additionally suppresses the WS2812 status LED during the night-mode window - see above for the full escalation/override interaction.

**Button (`button.py`):** polled (not IRQ-based) from an asyncio task, ~20ms recommended interval. Press bands: <50ms ignored (bounce), 50-1000ms = short press (fires `display.manual_next` on release), 1000-3000ms = dead zone (ignored entirely, avoids an imprecise release accidentally triggering either action), >=3000ms = long press (fires `pairing.start` once, while still held - not on release). Debounce window: 50ms. Re-entering WiFi setup mode is deliberately **not** a runtime press band - see below.

**WiFi (`wifi.py` + `identity.py`):** async STA connection (never blocks other tasks during connect attempts). On failure, caller applies capped exponential backoff (`next_backoff_s()`: 1s, 2s, 4s... capped at 60s) between retries. A dropped connection after initial success keeps retrying STA in the background rather than falling back to AP - sensors/display/BLE keep working without WiFi; only MQTT/HA connectivity degrades until reconnect. AP (setup) mode is an **open network** (no password, simplest for initial setup), SSID `GreenThumb-Setup-<base_id>`, entered automatically if no credentials are saved at boot. AP+STA run concurrently (ESP32 supports both simultaneously), so entering setup mode doesn't interrupt an existing connection. `base_id` (used here and in the MQTT topic tree) is the last 3 bytes of the WiFi MAC, uppercase hex - `core/identity.py`, shared by both.

**Re-entering setup mode: boot-hold, not a runtime press.** `wifi.check_setup_hold_at_boot(pin_num, hold_s=3)` is a blocking, one-shot check called from `main.py`'s startup sequence before the asyncio event loop starts - if the button is already held down at power-on and stays held for the full duration, the device boots into setup/AP mode instead of normal operation. This is intentionally separate from `button.py`'s runtime press detection: a runtime long-press (however long the threshold) could fire by accident if the device gets pinned against something during normal operation, which would be a serious problem for a device shaped like a fist meant to sit on a shelf. A hold-during-power-on cannot happen by accident.

**OLED setup-mode screen.** Whenever AP mode starts (fresh device with no saved credentials, or a boot-hold re-entry), `main.py` calls `disp.add_screen("setup", ...)` with the SSID `start_ap()` returned, showing "Connect to: `<ssid>` / Then visit: `<AP_IP>`" - using `wifi.AP_IP` (`192.168.4.1`, the ESP32 AP interface's default gateway, exposed as an explicit constant since `start_ap()` never reconfigures it away from that default) rather than a hardcoded string repeated elsewhere. Removed again via `disp.remove_screen("setup")` the moment `wifi_connect_loop()` sees a successful STA connection - a no-op if it was never added (the normal case: an already-configured device connecting on boot, no setup mode involved at all).

**Time sync (`ntp.py`):** MicroPython's `ntptime.settime()` sets the RTC to UTC with no timezone or DST support. `NtpSync` layers a fixed, user-configurable UTC offset (`timezone.utc_offset_hours`, supports fractional values like 5.5 for India) on top to derive local time for night mode and the daily light-hours midnight rollover (`local_time()` / `local_date()`). **No automatic DST** - a full timezone/DST rules database is far more than this project needs, so a region observing DST requires manually updating the offset twice a year; documented as a known limitation rather than solved. A single sync attempt (`sync_once()`) briefly blocks the event loop (typically well under a second) - accepted as a reasonable tradeoff rather than building a fully non-blocking NTP client. The background task (`sync_forever()`) re-syncs every 24h to correct RTC drift, retrying with capped exponential backoff (5s, 10s, 20s... capped at 5 min) on failure. Callers must check `is_synced()` before trusting `local_time()`/`local_date()` for anything correctness-sensitive (e.g. night mode) - an unsynced RTC returns `(0, 0)` rather than a plausible-looking wrong value.

**BLE pairing flow (`core/pairing.py`):** triggered by button long-press (3s) OR remote MQTT command. 60s scan window, blinking blue LED. Explicit user confirmation required even with only one candidate found (avoids accidentally pairing a neighbor's device). `start()` is synchronous - it launches the scan as a background asyncio task rather than awaiting it inline, so `handle_command()` dispatches every action (`start`, `select`, `cancel`, `acknowledge`) uniformly, and `button.py`'s synchronous `on_long_press` callback can call `start()` directly with no async wrapper. `cancel()` is valid even mid-scan; the in-flight scan task checks state on completion and discards its results if cancelled, rather than reviving a stale candidate list. `acknowledge()` is a separate action from `cancel()` for closing out a *successful* pairing - overloading `cancel()` for that would read as "something went wrong" when nothing did.

Depends on two interfaces: `ble_central.scan(timeout_s)` (async, returns discovered `{"address", "type", "serial"}` candidates) and `module_manager.register(address, mod_type, serial)` (returns a `mod_id`, stable across re-pairing the same physical module via its BLE serial). `pairing.py` was built against these documented contracts before either module existed.

**Bug found and fixed while building `module_manager.py`:** the interface above originally had `register(address, mod_type)` reading the module's BLE serial itself - but that requires an async BLE connection, while `pairing.py`'s `select()` (which calls `register()`) is deliberately synchronous. Fixed by moving the serial read into `ble_central.scan()`'s existing brief connection (which already reads Device Type, so reading Module Serial in the same connection costs nothing extra) - `register()` is now a pure, synchronous registry operation with no BLE involved, matching what `pairing.py` actually needs. Caught before either module was used together, not after.

**`module_manager.py` details:** registry is keyed by **BLE serial**, not address - serial is the one thing guaranteed stable across a module reboot (and, less commonly, an address change, since some BLE stacks rotate random addresses). `mod_id` is derived deterministically from the serial itself (not an incrementing counter), so re-registering the same physical module produces the same `mod_id` even after a full registry wipe - verified by test, not just asserted. `relay_forever()` maintains a BLE connection to every registered module, relaying State notifications to MQTT and publishing online/offline status; `send_command()` relays MQTT commands down to a module over its active connection, returning `False` (no ack channel exists, same as everywhere else in this design) if the module isn't currently connected.

**Known simplifications in the relay, flagged rather than glossed over:** no enforcement of the ESP32's concurrent BLE connection limit (~3-9 connections) once the registered-module count exceeds it; per-module reconnect uses a fixed retry delay rather than the capped-exponential-backoff pattern used elsewhere (`wifi.py`, `ntp.py`, `mqtt_client.py`); and the `on_module_health` hook (for a module to contribute to overall health, e.g. "reservoir empty") is accepted but unwired - no real module type exists yet to define what a health contribution even looks like.

**BLE GATT schema** (module side):
```
Service: a1e50000-b5a3-4393-b673-5d2a1d3d0001
├── Device Type      (...0002) Read
├── Module Serial     (...0003) Read
├── State              (...0004) Read, Notify   - mirrors MQTT module/state JSON shape
├── Command            (...0005) Write           - mirrors MQTT module/command JSON shape
└── Firmware Version   (...0006) Read
```
MTU negotiation attempted at connect; falls back to chunked fragments (header byte = sequence number, 0xFF = final) if negotiation fails.

**Implementation (`core/ble_central.py`):** `scan(timeout_s)` filters advertisements by the service UUID above, briefly connects to each match to read its Device Type characteristic (advertising payloads are too small to carry that reliably), then disconnects - candidates that fail during this brief connect are excluded rather than surfaced as broken. `ModuleConnection` wraps an established connection: attempts MTU negotiation once at connect, and `write_command_json()`/`subscribe_state()` transparently chunk or reassemble as needed - chunked-vs-unchunked is detected by checking whether the first byte of a notification is `{` or `[` (0x7B/0x5B), values far outside the 0-254 sequence-number range for anything but an implausibly large fragment count.

**Two notes on this module, one resolved:**
1. **`aioble` API confirmed against actual source** (not just memory) - `exchange_mtu(mtu=None, timeout_ms=1000)` and the resulting `.mtu` attribute are both real, verified via `micropython-lib`'s `aioble/device.py` on GitHub. No third-party alternative to `aioble` exists in real use for MicroPython BLE central work - the only fallback is the raw built-in `bluetooth` module that `aioble` itself wraps (IRQ-callback based, not async - MicroPython's own docs recommend `aioble` over it for most applications).
2. **Testing limitation still stands:** no BLE hardware in this project's dev sandbox. Functional tests cover this module's own logic exhaustively (chunk splitting/reassembly math round-tripped across many payload sizes, MTU fallback decisions, scan filtering/dedup, chunked-vs-unchunked detection) against a hand-written `aioble` mock built to the now-verified API shape - real BLE radio behavior (timing, actual peripheral quirks) can still only be confirmed on real hardware.

**Board choice:** ESP32-C3 Super Mini, confirmed after comparing against Pico W/2W (BLE+WiFi share a bus to an external co-processor chip - more contention risk), Pi Zero W/2W (full Linux, would require abandoning the MicroPython architecture), Wemos D1 Mini (ESP8266, no BLE at all), and ESP32-S3/original ESP32 (dual-core alternatives at similar price - would reduce CPU-level WiFi/BLE contention, but user has C3 units on hand already).

## Web portal (`web/server.py`)

No authentication - trusted home LAN, same assumption most local IoT devices make. Plain server-rendered HTML with minimal vanilla JS planned for later live-updating pages (not needed yet for a static setup form) - no SPA framework, no build pipeline, matching the ESP32-C3's limited RAM.

**Deliberately narrow HTTP server**, not general-purpose: GET for pages/static assets, POST with a bounded (`_MAX_BODY_BYTES` = 2048) `application/x-www-form-urlencoded` body. No chunked transfer encoding, no HTTPS. Built on `asyncio.start_server` (a standard MicroPython asyncio primitive) rather than a vendored web framework - reasonable for the current and near-term page count, revisit if the page count grows substantially.

**WiFi setup flow (first and so far only page set):** `GET /` serves the setup form, `POST /save` parses the submitted SSID/password, saves to config, calls `wifi.set_credentials()` (added to `WifiManager` for this purpose) and attempts a live `connect_sta()` - so the result page can say "Connected! IP: ..." or "Could not connect, check credentials" without requiring a reboot to find out. Credentials are saved to config regardless of whether the connection attempt succeeds, so they're there to inspect/retry rather than lost on a failed attempt.

**Two real bugs found and fixed by testing, not left unlabeled:**
1. `url_decode()` originally converted each percent-decoded byte to its own `chr()` independently, which mangles multi-byte UTF-8 characters (an SSID like "café" decoded as mojibake). Fixed by accumulating into a byte buffer and UTF-8-decoding once at the end.
2. That fix introduced a new failure mode: a fully malformed byte sequence (a stray UTF-8 continuation byte with no valid multi-byte sequence around it) raised `UnicodeDecodeError`, which would have crashed the request handler on a malformed client input. Fixed with a graceful fallback (lossy byte-per-character decode, which can never raise) rather than letting a bad request take down the handler.

**Dashboard (`GET /`, once WiFi credentials exist; `GET /api/state` for the underlying JSON):** live-updating via minimal vanilla JS polling `/api/state` every 5s - no SPA framework. Reads from a `state_provider()` callable injected into `WebServer`, documented as a contract ahead of `main.py` existing (same pattern as `pairing.py`'s `ble_central`/`module_manager` interfaces): a dict of `temp_f`, `humidity_pct`, `soil_moisture_pct`, `light_fc`, `health` (`{"status", "reasons"}`), `wifi_ip`, `mqtt_connected`, and optionally `modules` (list of `{"mod_id", "type", "online"}` - defaults to `[]` if the provider omits it, so a provider written before `module_manager.py` existed keeps working unchanged) - deliberately the same field set already shown on the OLED display, so all three surfaces (OLED, dashboard, HA) stay consistent. Missing readings render as "—" in the UI, never a fabricated number. If no `state_provider` is supplied (e.g. a server instance only being used for the setup flow), `/api/state` returns a safe all-`None`/disconnected default rather than crashing.

**Device name (`config.device_name`, default "Green Thumb"):** user-configurable directly from the dashboard (not just via HA) - a pencil icon next to the title opens an inline edit field, `POST /api/set_name` saves it. Bounded to 40 characters, since this name may eventually also render on the 16-char-wide OLED display. Read directly from config by the server itself, not through `state_provider` - it's a device setting, not sensor data, so it's always available regardless of whether `main.py`/`module_manager.py` exist yet.

**Modules section:** a reserved area on the dashboard for paired BLE modules, currently showing "No modules paired yet" until `module_manager.py`'s registry is wired in via `state_provider`'s `modules` field. Each module renders as a small card (formatted type name + an online/offline status dot) once real data exists - no per-module-type customization yet, matching how little is defined about any specific module (the watering pump) so far.

**Light Today (`GET /api/light_hours_today`):** replaces the dashboard's instantaneous `light_fc` reading with today's cumulative light duration so far (`light_tracker.get_light_hours_today()`, formatted as "3h 24m"), shown against the configured `light_hours_target` range. Deliberately **static on page load**, not part of the 5s-polled `/api/state` cycle - a separate endpoint and a separate `light_hours_provider()` callable exist specifically so this value's refresh cadence isn't coupled to the other readings'. A manual refresh button (↻) re-fetches it on demand. `light_fc` itself remains in the `state_provider` contract for other consumers (OLED, MQTT) - only the dashboard stopped displaying it directly, in favor of this cumulative view.

**Same on-demand model extended to MQTT/HA:** `{"action": "get_light_hours_today"}` on the base `command` topic triggers an immediate publish to a new retained topic, `greenthumb/<base_id>/light_hours_today` (`{"light_hours_today": float or None}`) - mirroring the dashboard's refresh button so HA can request a fresh reading the same way, via a button/script entity, rather than waiting for the next periodic state cycle. Wired through a new `on_get_light_hours_today` callback on `GreenThumbMqtt`, same pattern as every other command callback; silently no-ops if nothing is wired up yet (consistent with the rest of the command-handling design).

**Settings page (`GET /settings`, `GET /api/settings`, `POST /api/settings/save`, `POST /api/settings/mqtt`):** thresholds (temp/humidity/soil/light, each with green/red min-max), light tracking config, timing, display/night-mode, status LED, and timezone - all editable from one page, organized into collapsible sections. Reuses `config.get_by_path`/`set_by_path` directly - the same validated path-setter the MQTT `set_config` command uses - via a `_SETTINGS_FIELDS` mapping of `(form field name, config path, type, nullable)` tuples, so the settings page is a thin form↔config layer, not a second implementation of validation.

**Advanced settings toggle:** two sections - Direct Light Target and Light Sensor Mode (both described below) - are hidden by default behind a "Show advanced settings" checkbox, persisted via `localStorage` so it stays open across visits for anyone who uses it regularly. These are meaningfully more niche than the core threshold/timing fields, so hiding them by default keeps the main settings flow from being overwhelming for most users while still making them reachable.

**Excluded from the settings page, flagged rather than silently omitted:**
- Raw calibration values (`soil_calibration.dry_raw`/`wet_raw`, `light_calibration.dark_raw`/`bright_raw`/`bright_fc`) - only meaningful as output of the guided calibration procedure, which validates the two readings differ enough to matter (see `core/calibration.py`). Editing them as bare numbers here would bypass that validation entirely. The settings page shows **read-only calibration status** (calibrated yes/no per sensor, computed directly from config); actual (re)calibration happens on the dedicated calibration page (`/calibration` - see below).
- `light_mode.points` (multi-point light level samples, see below) - same reasoning as calibration values. Handled via dedicated add/remove/sample endpoints, not the generic `_SETTINGS_FIELDS` list, since raw values here should come from a live sample too, not be hand-typed.

**Per-field save behavior:** a submission with 30+ fields is applied field-by-field, but saved to flash **once** at the end, not once per field. A field that fails type coercion (e.g. non-numeric text in a number field) is skipped individually rather than aborting the whole submission - one bad value doesn't block the other 29 good ones. Unrecognized form fields are silently ignored, keeping the handler forward-compatible with a settings page that adds new fields without needing this handler updated in lockstep, as long as the field is registered in `_SETTINGS_FIELDS`.

**MQTT broker configuration**, previously a documented gap in `docs/BUILD.md` ("no UI yet"), is now closed via this page. Saving triggers a live reconnect attempt (same "try it now and report success/failure" UX as the WiFi setup flow) via a new `GreenThumbMqtt.set_broker()` method, mirroring `wifi.py`'s `set_credentials()` pattern - rebuilds the underlying `MQTTClient` with new settings and marks disconnected so `reconnect_forever()` also picks up the change on its next attempt regardless of whether the immediate connect succeeds. An empty password field on re-save means "leave the existing password unchanged," not "clear it" - so adjusting the broker address without retyping a password you don't want to change doesn't wipe it. Settings are saved to config even if the live connect attempt fails, so they're there to inspect/retry rather than lost.

**Direct Light Target (`light_tracking.high_intensity_hours_target`, advanced setting):** optional min/max hours of direct/high-intensity light per day - "some plants need X hours of direct light daily." Was dead config in an earlier revision of this schema (defined, never consumed by `light_tracker.py`) - fixed: `light_tracker.py`'s `_build_summary` now evaluates it as a **separate** `high_intensity_status`/`high_intensity_reason` pair, gated on both a target (min or max) being configured **and** `thresholds.light_fc.red_max` also being set (without that, "high-intensity" isn't measurable at all - `high_intensity_minutes_today` stays at zero regardless of what the target says, so evaluating against it would misreport "always failing" for something that simply isn't tracked yet). This status **never escalates or overrides** the primary light-hours status - it's informational only, matching the "non-essential" framing this was explicitly built with.

**Light Sensor Mode (`light_mode`, advanced setting):** a choice between the existing continuous-fc calibration ("single") and a new **multi-point** mode - instead of/alongside a numeric fc value, the user samples named reference points (e.g. "Direct Sun", "Bright Shade", "Low Light" - examples, not a fixed set; any label, any number of points) by holding the sensor in that condition and pressing "Sample Now" (`GET /api/settings/sample_light`, via a `light_raw_sample_provider` callable - documented contract ahead of `main.py`, same pattern as `state_provider`). `drivers/light_sensor.py`'s `classify_light_level(raw_value, points)` is a pure nearest-neighbor function - given the current raw reading and the configured points, returns whichever point's raw value is closest. No interpolation; ties resolve to whichever point is listed first (deterministic, and in practice ties on a live ADC reading essentially never happen). The dashboard shows the result as a "Light Level" badge, only when `state_provider` populates the optional `light_level_label` field (absent/null when in single mode, or before this is wired up) - never shown blank.

**Per-category duration tracking is deliberately NOT built here.** Tracking how long the sensor spent at each configured light level over the course of a day (e.g. "3h in Direct Sun today") is flagged as a **future Home Assistant integration roadmap item** instead (see `README.md`) - HA has far more room for that kind of historical/statistical tracking (long-term storage, graphing, statistics) than this device does, and it's a meaningfully different feature from the instantaneous classification built here.

**A real testing-process finding, not a code bug:** while testing this page, default-value assertions failed unexpectedly - traced to `storage.py`'s hardcoded `/config.json` path being a real, shared file on the development sandbox's filesystem that had accumulated state from dozens of earlier test runs across the whole project (WiFi credentials, calibration values, threshold changes) with no isolation between them. Not a defect in the shipped code - a real device only ever has one `config.json`, persisting across reboots is the correct behavior - but a gap in how these tests were being run. Fixed by overriding `config.CONFIG_PATH` to an isolated temp file per test run (the same pattern already used for `module_manager.py`'s registry tests), and re-verified every affected assertion against genuinely clean defaults.

**Dark mode:** CSS custom properties (`--bg`, `--card-bg`, `--text`, `--accent`, etc.) defined in `:root` and overridden under `[data-theme="dark"]`, applied to all three pages (setup, result, dashboard) since they share one stylesheet. Detection/persistence: `localStorage` (a real browser API - not to be confused with the Artifacts-sandbox restriction against it) holds an explicit user choice; absent that, `prefers-color-scheme` sets the initial default. The theme-detection script runs in `<head>`, before first paint, specifically to avoid a flash of the wrong theme - the toggle button's click-handling logic lives separately at the bottom of `<body>`, since it needs the button element to exist first.

**A real bug caught by `py_compile`, not by inspection:** an earlier docstring edit to `web/server.py` left an orphaned text fragment and a stray closing `"""` in the file, a syntax error that would have gone uncaught without re-running the compiler immediately after the edit - a reminder that "the edit looks right" isn't the same as "the file is valid," especially after a partial `str_replace`.

## Build (`tools/build_mpy.sh`)

Precompiles `core/`, `drivers/`, and `web/server.py` to MicroPython `.mpy` bytecode via `mpy-cross`, mirroring the source tree into `build/` (gitignored, regenerated each run). `boot.py`/`main.py` are deliberately left as plain `.py` (tiny bootstrap entry points, easier to debug/patch live via the REPL without recompiling), and `web/static/*` (not Python) is copied unchanged.

**Real constraint, not optional:** `mpy-cross` output is tied to the exact MicroPython version (and often architecture/feature set) it was built from - a mismatched version produces `.mpy` files that fail to load on the device. The script cannot verify this for you; check the device's version via the REPL (`import sys; sys.implementation`) and use a matching `mpy-cross` build. The script fails with a clear error (not a silent skip) if `mpy-cross` isn't found on `PATH` at all.

**Why bother:** precompiling reduces both flash footprint and import-time RAM/CPU overhead (MicroPython doesn't recompile `.py` source fresh every boot) - a real, standard optimization for a project this size (~130KB of source across `core/`+`drivers/`+`web/` as of this writing), not a guess.

**A real bug caught by testing, not assumed away:** an early version of this script, run from the wrong working directory during development, silently compiled a stale scratch copy of `core/` instead of the actual repo - `config.py` and `storage.py` were missing from the output with no error at all. Root cause: the script self-locates its repo root relative to its own file path, and it had been placed outside the actual repo during testing. Fixed by placing it correctly and re-verifying full file coverage (all 12 `core/` files, all 7 `drivers/` files, `web/server.py`, and static assets) before trusting the output.

## Calibration and pairing pages (`GET /calibration`, `GET /pairing`)

**Both pages reuse the exact same command-handler functions `main.py` builds for MQTT** - `calibration_command_handler`/`pairing_command_handler`, injected into `WebServer` alongside `calibration_manager`/`pairing_manager` (for read-only `status()` queries). A calibration or pairing action triggered from the web UI goes through the identical code path as one triggered from Home Assistant, including the MQTT status republish and (for pairing) the status LED update those handlers already do - the web routes don't reimplement any of that, they just build a payload dict from form fields and call the same function object. Verified directly: a full soil calibration flow and a full pairing flow, both driven purely through the web routes, correctly triggered the same publish/LED side effects the MQTT path would have.

**Calibration page:** two sections (soil, light) rendered from one `/api/calibration/status` response, since `core/calibration.py` is one state machine shared by both targets (only one can be active at a time - see that module's docstring). **A real logic bug caught by re-reading before testing, not by the test itself:** an early version computed each section's displayed state via `isActiveTarget ? status.state : "idle"` - which meant the *inactive* section always showed "idle" (a Start button) even while the *other* target was genuinely mid-calibration, making the intended "another calibration is in progress" blocking message unreachable dead code. Fixed by separating "nothing active anywhere" from "something else is active" as two distinct cases, and verified with an isolated Node.js test of the extracted decision function before it went back into the page - all three cases (globally idle, this target active, other target active) confirmed correct.

Each read step (`read_dry`/`read_wet` for soil, `read_dark`/`read_bright` for light) blocks on the device for ~2s (10 averaged samples - see `drivers/soil_moisture.py`/`light_sensor.py`), so the button shows a "Reading... (~2s)" disabled state during the fetch rather than looking unresponsive. Light's save step requires a `bright_fc` reference value typed in at that point (there's no way around needing an external light reference - see the light calibration section above); soil's save step needs nothing extra.

**Pairing page:** `start` kicks off the shared 60s scan; the page polls `/api/pairing/status` every 2s only while `state == "scanning"` (stops immediately once the state changes, whether to `awaiting_select` or back to `idle` if nothing was found - polling is not a general-purpose refresh loop). Candidates render as cards with a "Pair This" button per module; `select` is always required even with only one candidate found, matching the pairing state machine's own design (avoids silently pairing a neighbor's device). `acknowledge` closes out a successful pairing and returns to idle, ready for `start` again.

**Discoverability:** the settings page's read-only calibration status section links to `/calibration`; the dashboard's Modules section header gained a small "＋" link to `/pairing`.

**Provisional module development contract (no real module firmware exists yet to validate against - flagged as such, matching how `ble_central.py`/`module_manager.py`'s interfaces were built ahead of real modules earlier):** a module's `State` JSON may optionally include:

```json
{
  "name": "Tomato Pump",
  "description": "Drip irrigation for the tomato bed",
  "config_required": true,
  "config_options": [{"key": "flow_rate", "label": "Flow Rate", "type": "float"}],
  "data_sources": [{"key": "reservoir_pct", "label": "Reservoir Level", "unit": "%"}],
  "needs_calibration": true,
  "calibration_fields": [{"key": "prime_time", "label": "Prime Time", "type": "int"}]
}
```

Every field is optional and defaults gracefully if absent (`main.py`'s `_build_module_summary` mirrors the same `.get(key, default)` pattern already used for `calibration_fields`). **`name` is module-assigned, not base-editable** - unlike the base's own `device_name` (which the user renames from the dashboard), a module's display name is entirely the module's own to set and report; the base is a pure passthrough with no rename mechanism of its own. The dashboard falls back to a formatted `type` string when `name` is absent.

**`type` is the one field that does NOT flow through `State`** - it's read once during pairing from the `Device Type` GATT characteristic (see the GATT schema above) and stored in the registry, available even before the module has sent its first `State` notification. Suggested category values: `light`, `water`, `soil`, `misc`, etc. - examples, not a fixed enum; add categories as needed.

`config_options`/`calibration_fields` share the same `{"key", "label", "type"}` shape deliberately, for a consistent generic-form-rendering pattern on the base's UI regardless of which one is being filled in. The base sends values back via `Command` as `{"action": "set_calibration", "values": {...}}` (calibration) - pure passthrough either way, the base never interprets field names or values, since it has no way to know what any given module type actually expects. If a module hasn't reported `calibration_fields` (nothing built yet), the calibration page falls back to a generic key/value entry UI rather than a broken empty form.

**Name collisions and the `set_name` action.** Two modules of the same type will often share the same factory default name (both a "Water Pump," say) - the base actively guards against this rather than just displaying a confusing duplicate. `module_manager.py`'s `_resolve_name_collision(mod_id, state_dict)` runs **once**, on a module's first-ever `State` report after connecting (not on every subsequent update - a name the user or module later changes deliberately is never fought with): it checks the newly-reported `name` against every other currently-known module's cached name, and on an exact match, pushes a disambiguated version back via `Command` as `{"action": "set_name", "value": "Water Pump 2"}` - incrementing the suffix (`" 2"`, `" 3"`, ...) until no collision remains. The **same action** is used for the user-facing side of this: the pairing page's post-pairing screen offers an optional "set a custom name" field (`POST /api/modules/set_name`), sent through `module_manager.send_command()` exactly like the automatic push - a module only needs one handler to cover both cases. Neither path updates `module_manager`'s registry or forces anything; the base's cache reflects whatever the module reports back on its next `State` update, same as any other module-owned field.

**A real race condition caught and fixed before it ever manifested:** if two modules both connect for the first time in close succession, before either has had a chance to report back its disambiguated name, a naive implementation could have both see the same stale "collision count" against each other's original (pre-disambiguation) cached name - and both get pushed the identical `"Water Pump 2"`, still colliding. Fixed by optimistically updating the cache immediately after computing a disambiguated name (before the module has confirmed adopting it, not after) - self-corrects if the module ends up reporting something different. Verified directly: three modules connecting in sequence correctly land on `"Water Pump"`, `"Water Pump 2"`, `"Water Pump 3"`, with the third's collision check confirmed to see the second's optimistically-updated cache rather than its stale original name.

**This exposed a real gap, now fixed:** `module_manager.py`'s relay previously *discarded* each module's State after forwarding it to MQTT - nothing cached it, so there was no way for the dashboard/calibration pages to read `needs_calibration` at all. Added `get_last_state(mod_id)` (returns `None` if never received - legitimately possible for a short window right after pairing, since `relay_forever()` picks up newly-registered modules on a 5s cycle, not instantly) plus a small cache populated by the same `on_state` callback that already published to MQTT.

**Generic passthrough endpoint:** `POST /api/modules/calibrate` (form fields: `mod_id`, plus any number of `cal_<key>=<value>` pairs) extracts the `cal_`-prefixed fields into a `values` dict and calls `module_manager.send_command(mod_id, {"action": "set_calibration", "values": values})` directly - no new sync/async wrapping needed here (unlike the MQTT callback case caught earlier) since web request handlers are already `async`. Returns `success: false` with an explanatory error (not a 500) if the module isn't currently connected, and 503 if no `module_manager` is wired at all - both handled gracefully rather than crashing the request.

**Dashboard:** each module card gained a "Calibrate" link to `/calibration?module=<mod_id>` (deep-links to and highlights that module's card there), shown as "⚠ Calibrate" in a warning color when `needs_calibration` is true.

**Pairing page:** after a successful pairing, since the module isn't necessarily connected the instant pairing completes (see the 5s relay cycle above), the "paired" screen polls `/api/state` for up to ~20s (every 2s) waiting for that module to come online and report its calibration status, then shows either a "needs calibration" prompt linking to `/calibration?module=<mod_id>` or a "no calibration needed" note - rather than either blocking the UI or guessing before the data exists.

**A real logic bug caught by an isolated Node test before it ever ran in a browser:** the module-calibration-card renderer needed to choose between typed inputs (when a module reports `calibration_fields`) and a generic key/value fallback (when it hasn't) - verified with 4 extracted-logic test cases, including the easy-to-miss case of `calibration_fields` being `undefined` entirely (not just an empty array) and an empty generic key correctly producing no malformed `cal_` field.

## main.py / boot.py / pins.py / version.py

**`boot.py`** adds `/core`, `/drivers`, and `/web` to `sys.path` - this is a real fix, not always-been-there plumbing. **A genuine bug, previously undetected, caught only while wiring up `version.py`'s cross-directory import:** every file in this project uses flat imports (`import wifi`, `import display`, `import pins`, etc.) on the assumption that each other's directories are already searchable, but `boot.py` never actually did this - MicroPython's default `sys.path` only resolves imports at the filesystem root, so `main.py`'s very first cross-directory import would have failed immediately with `ImportError` on real hardware. This was masked the entire time by the `main.py` smoke-test harness, which manually replicated the *intended* `sys.path` setup in the test script itself rather than exercising the real (at-the-time-empty) `boot.py` - the harness was accidentally testing what `boot.py` was supposed to do, not what it actually did. Fixed, and a regression check added to the smoke test that reads `boot.py`'s actual source and asserts all three directories are referenced - the kind of check that would have caught this the first time.

**`version.py`** is a plain constants file (matching `pins.py`'s pattern - a fact about which code is running, not a user-editable setting, so it stays out of `config.py`). Semantic versioning (MAJOR.MINOR.PATCH), bumped manually by whoever changes the code - MAJOR for breaking MQTT-contract/config-schema changes, MINOR for new features, PATCH for fixes. Starting at `0.1.0`, not `1.0.0`: the base's own feature set is mature, but nothing has been verified on physical hardware yet and neither the HACS integration nor a first real module exist - see README's checklist. Published via `mqtt_client.py`'s `publish_device_info()` to a new retained topic, `device_info` (version, `device_name`, `friendly_name`, `base_id`) - kept separate from the mutable `config` topic since it reflects fixed identity facts, not settings. Exists specifically to give the future HACS integration a `sw_version` for its device registry entry - nothing previously published the *base's own* firmware version anywhere (only BLE modules had one, via the `Firmware Version` GATT characteristic).

`friendly_name` (0.3.0) is additive - the same value as `device_name`, under a second key, for other MQTT clients that want a human-readable label without needing to know `device_name` specifically is the field to read (e.g. a future camera module's own MQTT discovery, which needs something to show besides the raw MAC-derived `base_id`). Falls back to `config.DEFAULT_CONFIG`'s own `device_name` default (`"Green Thumb"`) if `device_name` is empty/unset, rather than falling back to `base_id` - defeating the entire point of the field by showing the raw identifier anyway would be worse than a generic name. `device_name`/`version`/`base_id` are unchanged.

**`pins.py`** is a plain constants file (not part of `config.py` - these are hardware wiring facts fixed at deployment, not user-editable runtime settings), grounded in cross-referenced public ESP32-C3 Super Mini pinout documentation, not just memory:

| Signal | Pin |
|---|---|
| Soil moisture (ADC) | GPIO0 |
| Light sensor (ADC) | GPIO1 |
| DHT11 data | GPIO3 |
| Button | GPIO10 |
| I2C SDA (OLED) | GPIO4 |
| I2C SCL (OLED) | GPIO5 |
| WS2812 data | GPIO6 |

**Confirmed against a physical board photo (ACEIRMC ESP32-C3 Super Mini)** - the back-of-board silkscreen clearly labels both pin columns (left: 5V/G/3.3/4/3/2/1/0, right: 5/6/7/8/9/10/20/21), and every pin assigned below is physically present on that specific board. No longer a documentation-only proposal for this vendor; still worth a silkscreen check if using a different "Super Mini" clone, since labeling has been reported to vary slightly across them.

GPIO0/1/3/10 are the four pins explicitly identified across sources as carrying no strapping, flash, USB, or JTAG duties. Only 4 such unambiguous pins exist against 7 needed signals, so I2C and the WS2812 line land on GPIO4-6 - sources disagree on whether these carry JTAG duties or are freely available; flagged rather than silently picked, and accepted since this project has no hardware JTAG debugging planned (development uses the native USB REPL). GPIO2/8/9 (strapping pins, one also driving the onboard LED and one wired to the BOOT button), GPIO12-17 (not broken out), GPIO18/19 (native USB), and GPIO20/21 (default UART/REPL) are avoided entirely. **An analog/digital multiplexer was considered and rejected** for this board: I2C doesn't need one (already a shared bus, single display, no address conflicts), an analog mux would trade 2 ADC pins for 1 ADC pin + select lines (a net pin *increase* for only 2 signals), and future capability arrives via separate BLE modules with their own microcontrollers, not more direct sensors on the base board - so there's no growth pattern here a mux would actually serve.

**`main.py`** wires every driver and `/core/` module into a running asyncio task set. Two things resolved here that were previously flagged as open items, not newly discovered:

1. **The `ntp.is_synced()` night-mode gating** (see the display/night-mode section above) - `display.py`'s `now_provider` is wrapped (`_display_now_provider`) rather than passed `ntp.local_time` directly: while unsynced, it returns a fixed `(12, 0)`, which fails safe (stays outside any reasonable night-mode window) rather than risking an unsynced `(0,0)` reading incorrectly evaluating as "inside the night window." The status LED's night-mode check in `led_tick_loop` is gated the same way, independently.
2. **A sync/async mismatch, the same class of bug caught earlier between `pairing.py` and `module_manager.py`**: `mqtt_client`'s `on_module_command` callback fires synchronously (from `check_msg()`'s dispatch chain), but `module_manager.send_command()` is `async def`. Passing it directly would have silently created a coroutine object that never runs. `_handle_module_command` wraps it in `asyncio.create_task(...)` instead - fire-and-forget, matching how `pairing.py`'s own `start()` already launches its scan as a background task rather than being awaited inline.

**A third bug, this one caught by the smoke test built specifically for this file, not by inspection:** `module_manager.ModuleManager(ble_central, mqtt, ...)` passes `mqtt` as a direct constructor argument - evaluated immediately, unlike the callback closures elsewhere in the same function that safely forward-reference names assigned later (those aren't evaluated until actually called, long after setup finishes). `mqtt` wasn't constructed until several lines later in the original draft, producing an `UnboundLocalError` the moment `main()` actually ran. Fixed by moving `mqtt`'s construction (and its callback closures, which safely forward-reference `module_mgr`/`pairing_mgr`/`cal_mgr`) before `module_mgr`/`pairing_mgr`.

**Testing approach for this file, and why it needed one of its own:** `main.py` calls `asyncio.run(main())` unconditionally at module level - importing it normally in a test would hang forever (or until a real reboot), since `main()` never returns by design (it ends in an idle loop keeping the event loop alive while background tasks do the real work). Verified instead with a dedicated smoke-test harness: every hardware/MicroPython-only dependency mocked (`machine`, `dht`, `ssd1306`, `framebuf`, `neopixel`, `network`, `ntptime`, `umqtt.simple`, `bluetooth`, `aioble`, plus MicroPython's `time.ticks_ms`/`ticks_diff` and `asyncio.sleep_ms` extensions), `asyncio.run` monkeypatched to run `main()` under a 2-second bound via `asyncio.wait_for` instead of forever, then the actual file executed via `exec()` so the module-level call triggers the patched version. A clean pass (reaching the idle loop without raising) confirms the wiring is structurally sound - argument counts, attribute names, construction order - which per-module tests can't catch since this is the first point where every piece is actually assembled together. Verified both the fresh-device path (no WiFi credentials → AP mode starts) and the already-configured path (AP mode correctly skipped) - and confirmed `publish_loop()` and `sensor_loop()` actually exchanged data correctly, not just "didn't crash": the observed MQTT publish sequence included `state`/`health` topics, which only `publish_loop()` sends, reading fields only `sensor_loop()` writes - if either used a wrong key name, this would have raised a `KeyError` rather than silently passing.

## Alert light and sensor failure tracking

**`status_led.set_alert(active)`** - a generic catch-all signal, distinct from health-status escalation, for any unexpected condition a future caller might want to surface physically. Shown as a slow alternation between the current health color and solid red, `_ALERT_PHASE_MS` (5s) per phase - deliberately much gentler than the fast escalation blink so the two read as different signals. Priority: below pairing (an active, user-initiated action always wins), above WiFi-connecting. **Has no override option for night-mode DND at all**, unlike escalated red (which optionally can via `red_overrides_led_off`) - a deliberate, permanent asymmetry: escalation is specifically about health getting worse through a pipeline that already earned the override discussion, whereas alert is a broader mechanism whose eventual callers aren't fully known yet, so defaulting to always-respects-DND is the safer choice. Falls back to "off" as the non-red phase color if `health_status` is still `None` rather than guessing a color that was never reported.

**Sensor failure tracking (`config.sensor_failure`, `main.py`).** DHT11 is tracked unconditionally - a `None` reading from `dht.read()` always means a genuine failure, no calibration concept to gate on. Soil moisture and light are tracked too, but **only once their own calibration is complete** (`main.py`'s `_update_sensor_failure_tracking` is called with `calibrated_flag and reading is None`, not just `reading is None`) - before calibration, a `None` reading is a normal, expected state, and conflating the two would nag a new user about "sensor failure" for a sensor they simply haven't calibrated yet. Passing the calibrated flag *into* the failure check (rather than skipping the tracking call outright when uncalibrated) also correctly clears any previously-tracked failure if a sensor transitions from calibrated back to uncalibrated mid-recalibration, verified directly as its own test case.

Worth being honest about: once `soil_moisture.read_percent()`/`light_sensor.read_fc()` are genuinely calibrated, their only `None`-producing code paths *are* calibration-related (missing values, `dark_raw == bright_raw`) - there's no ADC-read-failure path that returns `None` the way DHT11's bit-banged protocol does. So this tracking is wired the same way as DHT11 for **uniformity and as a safety net**, not because a robust ADC-failure-detection heuristic was invented for these two sensors specifically. If a future firmware change adds real sanity-checking (e.g. flagging a suspiciously-stuck raw value), it flows through this same mechanism without needing rearchitecting.

**Two tiers**: `alert_after_s` (default 1h) surfaces in the health payload/dashboard only; `notify_after_s` (default 6h) additionally engages `status_led.set_alert()`. **Dismiss** (`{"action": "dismiss_sensor_alert", "sensor": "..."}`, same shared-handler pattern as `set_name` - one function wired to both the MQTT `on_command` dispatch and `POST /api/dismiss_sensor_alert`) is scoped to the *current* failure episode, not permanent: `_update_sensor_failure_tracking` clears the tracked entry entirely on recovery, so a fresh failure after a real recovery starts un-dismissed - avoids permanently silencing a sensor that might fail again later for an unrelated, real reason.

**Multiple simultaneous failures (`sensor_failure.multi_alert_mode`)**: "combined" (default) aggregates simultaneously-qualifying alerts into a single display entry (`{"sensor": "multiple", "sensors": [...], ...}`) purely for presentation - each sensor is still tracked and timed completely independently, nothing about the underlying timing changes. A combined entry's `dismissed` is `True` only once *every* contributing sensor is individually dismissed - one undismissed sensor inside the group still means something needs attention. "layered" instead divides both thresholds by the count of *currently* failing sensors (open episodes, not just ones that have already crossed `alert_after_s`) before comparing - 2 concurrent failures halves both thresholds, 3 divides by 3, and so on, so the alert/notify tiers arrive progressively sooner the more things are wrong at once. Intended as a stronger, faster signal for a likely-systemic problem (a power or wiring issue affecting multiple sensors together) versus one isolated sensor acting up on its own. The dashboard's dismiss buttons always target the real underlying sensor key, even for a combined entry (`alert.sensors`, never the `"multiple"` placeholder itself, which was never a real tracked key and would just silently no-op).

**A real bug caught in my own test harness while verifying this, not the firmware:** an early test run showed sensor-failure tiers jumping straight from nothing to "notify," never passing through "alert." Traced to `dht11.py`'s retry logic correctly using real `time.sleep()` (not `sleep_ms`) for its datasheet-mandated 1s retry backoff between failed read attempts - entirely correct firmware behavior, already documented in that module's own docstring. The test harness had only mocked `time.sleep_ms`, not `time.sleep`, so each failed `dht.read()` call was silently consuming ~2 real seconds the accelerated test config didn't account for. Fixed the harness, then verified the full escalation and dismiss/recovery lifecycle end-to-end through real `main.py` execution (not just isolated logic) - a forced failure correctly progressing through `alert` → `notify`, a dismiss command correctly silencing it without requiring recovery, and a real recovery correctly clearing the episode so a subsequent fresh failure starts un-dismissed.

## Temperature display unit

`config.display.temp_unit` ("F" default | "C") is deliberately display-only - it converts the OLED Temp/Hum screen and the dashboard's live Temperature reading, and nothing else. `thresholds.temp_f` and every other stored/calibration value stay in °F internally always, regardless of this setting. Converting stored thresholds too was considered and rejected: a repeated F→C→F edit cycle (view in C, re-save) could drift a real health-relevant threshold by rounding over time, which isn't worth the risk for what's fundamentally a presentation preference. `main.py`'s `_format_temp()` and `dashboard.html`'s `fmtTemp()` implement the same conversion independently (Python and JS don't share code) - verified to agree exactly at the standard reference points (32°F=0°C, 212°F=100°C, 98.6°F=37°C) since a silent mismatch between the two would be a confusing, hard-to-notice bug.

## LED idle modes and colorblind-safe color schemes

**Idle display modes (`config.status_led.idle_mode`)** - how plain (non-escalated, non-alert) health status is shown: `"solid"` (default, steady color), `"breathe"` (slow sine fade, speed set by `idle_breathe_period_ms` - deliberately defaulting slower, 4000ms, than the 3000ms breathing used for boot/WiFi-connecting, since those signal "something's actively happening" and idle should read calmer), `"pulse_once"` (off except for one breathing-style pulse right after a status change, then back to off - a transient acknowledgment rather than a constant presence), or `"off"` (LED stays dark for plain health status specifically - pairing/WiFi-connecting/alert are all higher-priority tiers and still light up normally). All four are live-configurable, passed into `tick()` each call rather than baked into the constructor, matching the existing night-mode-parameter pattern.

`"pulse_once"` is driven by a timestamp (`_last_status_change_ms`), recorded unconditionally by `set_health()` on every genuine status change regardless of the currently-configured `idle_mode` (cheap bookkeeping) - `tick()` is the one that decides whether to actually render a pulse from it, since `idle_mode` is only known live at that point, not inside `set_health()`. This keeps `set_health()`'s call sites in `main.py` unchanged.

**Colorblind-safe and custom color schemes (`config.color_scheme`)** - independently configurable for the web portal and the alert LED (`web_portal`/`alert_led`, each `"default"` | `"colorblind"` | `"custom"`), with a `sync` flag that mirrors one onto the other at write time in `web/server.py`'s settings handlers - neither `status_led.py`'s `tick()` nor the dashboard's rendering code need to know "sync" exists, they each just read their own field, which happens to already equal the other's when synced. Colorblind mode swaps green for blue and red for orange (`(0,120,255)`/`(255,140,0)`, the standard deuteranopia/protanopia-safe pairing) - yellow is left alone, already distinguishable from both. Custom mode uses `color_scheme.custom_colors`, a single shared RGB-triple set (not per-surface) used by whichever surface(s) are set to `"custom"`.

**`status_led.py`'s `COLORS` constant was split** into `_FIXED_COLORS` (pairing/WiFi-connecting/off - never affected by the scheme, since the colorblind concern is specifically about the green/yellow/red health semantics) and health-tier colors, now threaded live through `tick()`'s new `health_colors` argument (a `{"green","yellow","red"}` RGB dict, or `None` for built-in defaults) rather than a fixed module constant - a settings change takes effect on the next tick, no restart needed. Applies consistently across every rendering path that shows a health color: solid idle display, escalated-red blink, the alert flash, and even the boot animation's breathing-green phase.

**The dashboard resolves its own scheme client-side** (`resolveHealthColors()` in `dashboard.html`), reading `data.color_scheme.web_portal` (the scheme name) and `data.color_scheme.custom_colors` (raw RGB arrays) - exposed via `main.py`'s `_get_dashboard_state()` the same way `device_name` already is (a device-level setting, not sensor data, using the same established precedent rather than requiring a second fetch to `/api/settings`). The dashboard's colorblind hex values (`#0078ff`/`#ff8c00`) are hand-verified to exactly match `main.py`'s `_COLORBLIND_HEALTH_COLORS` RGB tuple - the two surfaces don't share code (Python RGB tuples vs. JS/CSS hex strings), so this consistency is maintained by hand, not by import, and is worth re-checking if either ever changes.

**Confirmed directly, not assumed, per an explicit request to double-check:** both the read path (`mqtt_client.publish_config()` already dumps the *entire* config dict, so any new top-level key is automatically included with zero additional wiring) and the write path (the generic `set_config` MQTT action navigates by dot-separated path via `config.set_by_path`, which already handles arbitrary nesting) already cover every field added here - `color_scheme.sync`, `status_led.idle_mode`, all of it - without needing any new MQTT-specific code. Verified with a direct round-trip test (`set_by_path` on the new nested paths, then a full save/load cycle) before claiming this rather than just asserting it followed from the existing design.

## Bugs found by external code review

Five real bugs, caught by a review of this repo rather than by the testing done while building each piece - worth documenting as a class of thing automated tests here didn't catch, not just fixing silently.

1. **`requires_immediate_attention` silently dropped from most publishes.** `main.py`'s escalation callback correctly included the flag, but `sensor_loop()`'s red-transition interrupt publish and `publish_loop()`'s periodic publish both built the health payload independently and neither included it. Since `health` is a retained topic, the next periodic publish after an escalation (up to 30 min later) silently overwrote the retained payload and lost the flag - Home Assistant's view of "needs immediate attention" would go stale even while the LED was still physically blinking red. Fixed with a single `_build_health_payload()` function used by all three call sites, specifically so they can't independently drift apart again. Verified end-to-end (not just unit-level): forced a real red health condition through actual escalation via the full smoke-test harness with accelerated timing, and confirmed the flag correctly carries forward through subsequent periodic publishes rather than reverting to `False`.
2. **Calibration's "insufficient delta" error never displayed.** `core/calibration.py`'s `_save_soil`/`_save_light` reset `target` to `None` on this specific failure, while `calibration.html`'s error display checks `status.error && status.target === target` - with `target` cleared, that check is never true for either section, so the user just saw the Start button reappear with no explanation. Fixed by no longer clearing `target` on this specific error path (only `cancel()` and a successful save still clear it) - a successful `start()` afterward overwrites it regardless, so nothing lingers incorrectly. Verified the fix directly against `calibration.py`'s actual state machine, plus confirmed the existing asymmetric-recovery behavior (bad delta vs. missing `bright_fc`) and `cancel()`'s full-clear behavior both still work via regression tests.
3. **`tools/build_mpy.sh` never copied `pins.py`.** The script compiled `core/`, `drivers/`, `web/server.py`, and copied `boot.py`/`main.py`/`web/static/*` as-is - but `pins.py` (imported first thing by `main.py`) wasn't handled by either path at all. Following `docs/BUILD.md`'s own instructions would have produced a device that fails to boot with an import error. Fixed by adding `pins.py` to the compile step (it's a real importable module, not a boot entry point like `boot.py`/`main.py`, so it belongs there rather than in the copy-as-is path) - verified the actual build output now includes `pins.mpy`.
4. **`mqtt_client.set_broker()` didn't disconnect the old client** before replacing it with a fresh one - a small resource leak on broker-setting changes. Fixed with a `try`/`except OSError` disconnect call before rebuilding (the old client may never have connected in the first place, which would otherwise raise).
5. **`web/server.py`'s `_read_body()` didn't handle a client declaring a `Content-Length` it doesn't actually deliver** (e.g. a dropped connection mid-body) - `readexactly()` raising uncaught skipped straight past any response and closed the connection with nothing sent, instead of a clean 400. Fixed by catching `EOFError` (which `asyncio.IncompleteReadError` is itself a subclass of, so this covers both the CPython and MicroPython raise shapes) and returning an empty body, letting the existing downstream field validation produce the correct error response naturally.

## Future Enhancements

Documented ideas that are **deferred, not scheduled** - captured here so the reasoning and open questions aren't lost, not as a commitment to build them. See `decisions-and-practices.md` for the log entry on why this one specifically was documented instead of implemented.

### Species-based sensor threshold suggestions

**Status: deferred, not scheduled. Do not implement from this note alone.**

The idea: let a user optionally identify what a given base is monitoring, and use that to suggest sensor thresholds instead of leaving every base on generic-houseplant defaults.

- Add an optional `species` field, scoped **per base** (or per base's assigned camera-grid region, if the multi-base/camera-grid concept referenced elsewhere ends up shaped that way) - separate from and unrelated to the existing `device_name`/`friendly_name` fields, which stay purely display-only labels and would not be repurposed for this.
- If `species` is set, look up known ideal-condition data for that species (soil moisture %, light hours/day, etc.) from an external source and present it as **suggested** threshold values for that base's existing sensors (moisture, light, and so on). **Never auto-applied** - a suggestion only becomes a real threshold change after the user explicitly accepts/confirms it, same "nothing silently changes a real setting" posture as everywhere else config gets written in this project.
- **Data source not chosen.** Candidates surfaced so far - Perenual API, Trefle, Wikipedia infobox parsing - all have gaps or inconsistent units between species entries. This needs real research and evaluation before any is picked, not a default-to-whichever-is-easiest choice.
- **Open design question, deliberately left open:** does the Camera Module (it has spare compute and its own WiFi/MQTT presence - see `modules/Camera Module/`) perform the species lookup and relay results through the base's existing MQTT topic namespace, or does each base perform its own lookup independently? Answering this now would be guessing ahead of the actual implementation constraints (network access from the base vs. the module, request rate/caching, offline behavior) - left for whoever picks this up.
- **Explicitly unrelated to, and must never be merged with, the Camera Module's general-health classifier** (not yet built - see `modules/Camera Module/README.md`'s Status section for what exists so far). That classifier is intended to stay species-agnostic by design - a single generalized health score, with no species identification anywhere in the image-scoring pipeline. Recording that constraint here, ahead of the classifier itself existing, specifically so it isn't reconsidered/blurred later once this threshold-suggestion feature and the classifier are both being worked on. This feature only ever affects *suggested threshold values for other sensors* (moisture, light, etc.); it has no bearing on, and should never be wired into, how a photo gets scored.

### Gap: Base-firmware local UI cannot display settings for non-BLE-paired modules

**Status: deferred, not scheduled. Do not implement.**

The base firmware's local web portal (`web/server.py` / `core/`) currently has no mechanism to subscribe to or render MQTT data from a module it isn't BLE-paired with (e.g. the Camera Module, which is a standalone WiFi/MQTT module, not a BLE peripheral).

As of the current camera module work, per-base camera settings (general health/advanced metric toggles, etc.) are editable via HA and the camera module's own portal - full MQTT-layer parity exists - but are NOT visible/editable on that base's own local portal. This was an explicit scope decision on the camera module task (modifying base firmware was out of scope - different codebase, would require its own version bump and testing, not authorized under that task).

Closing this gap means: base firmware gains an MQTT subscription client-side for relevant module topics it isn't BLE-paired with, plus a new local-portal UI section to render/edit that data. This is base-firmware work (`core/`, `web/server.py`), with its own version bump and testing - separate from any module's `version.py`.

This isn't camera-module-specific - any future standalone WiFi/MQTT module (not just the camera) would hit the same gap. Worth solving generally (a base subscribes to and displays settings for any associated module, regardless of pairing method) rather than one-off per module.
